Extending ElastAlert 3
======================

ElastAlert 2 loads custom rule types, alerters, rule loaders, match enhancements and Jinja filters from Python
modules named in the rule (``type: mymodule.MyRule``). ElastAlert 3 is a compiled program and cannot load Python
code: every component is part of the binary, and a rule naming a Python class is **rejected at load** with a message.

To add a component, write it in Rust in your copy of the source and rebuild with ``cargo build --release``.
The unit tests live in a ``#[cfg(test)] mod tests`` block at the bottom of each file; run them with ``cargo test``.

.. _enhancements:

Match enhancements
------------------

This is the simplest extension point and the only one with a stable, documented interface: a type implementing the
``Enhancement`` trait plus one line in a registry. See :doc:`enhancements` for the built-in modules and a complete
example.

.. _writingrules:

Rule types
----------

Rule types live in ``src/types.rs``. ``RuleType`` is an enum with one variant per type, and three entry points:

- ``add_data``: receives the hits of a query, as compact events (timestamp, count, and the fields the type
  needs). Used by most types.
- ``add_count``: receives a document count, for ``use_count_query``.
- ``add_aggregation``: receives an aggregation result, for the aggregation rule types.

``garbage_collect`` is called at the end of each run with the current time, for types that alert on the absence of
events (``flatline``) or need to drop old state. Matches are pushed to the ``matches`` vector passed to each call.

A new type also needs its name in ``rule::load`` (``src/rule.rs``), with its required options and the fields it
needs fetched from Elasticsearch (field projection), and an alert text in ``src/alert.rs`` if it has its own sentence.

.. _writingalerts:

Alerters
--------

Alerters live in ``src/alerters/``, one module per alerter. ``src/alerters/mod.rs`` holds the ``Alerter`` enum, the
mapping from the ``alert:`` name to the module (``Alerter::from_rule``), and shared helpers to read options. Webhook
alerters use the shared HTTP client of ``http.rs`` (proxy, CA file, timeout, ignore SSL errors). Each module has:

- a constructor that reads and checks its options when the rule loads, so that ``elastalert validate`` reports
  mistakes;
- an ``alert`` function that receives the alert text (``View``) and the matches, and returns an error to have the
  delivery retried;
- tests using ``testutil``: a rule builder and an in-process HTTP capture server.

Rule loaders
------------

Only the file loader (``rules_folder``) exists. Rules can be generated by any tool that writes YAML files into the
rules folder: changed files are picked up every ``run_every``.

Jinja filters
-------------

Jinja templates are rendered with `minijinja <https://docs.rs/minijinja>`_, close to but not identical to Python
Jinja2. Custom filters (``jinja_filters``) are Python classes and are rejected at load; filters can be added to the
template environment in ``src/alert.rs``.
